## 1. 建议的首版范围

以下为提案，人数、联网场景和服务器条件待用户确认。

- 新增 Online Race：2–4 名真人通过房间码进行互联网竞速。
- 复用两条赛道、三圈、方向检查点、漂移加速、奖励门、碰撞和救援机制。
- 房主选赛道，玩家准备，全员准备且至少两人后由房主开始。
- 提供昵称、玩家列表、连接状态、倒计时、实时名次、个人完赛和最终结果、再来一局。
- 保留 Quick Race 与 Time Trial；联机成绩不写入单机计时纪录。
- 首版不含公开匹配、账号、全球排行榜、观战、AI 补位或跨服务器扩容。

## 2. 代码现状及改造重点

- Vite + TypeScript + Three.js；已提交 package-lock.json，沿用 npm。
- src/game/Game.ts 同时负责本机输入、模拟、AI、渲染与流程编排。
- src/entities/ArcadeBoat.ts 将运动状态与 Three.js 对象绑定；先拆模拟状态与显示适配。
- src/core/Loop.ts 用 requestAnimationFrame 的帧间隔更新；模拟需改用固定步长。
- src/game/RaceManager.ts 在本机玩家完赛时结束比赛；多人需分别记录个人和全场结束。
- Player 的固定 player ID 需替换为联机稳定席位 ID，本地视角通过独立标识选择。
- CollisionSystem、InteractionSystem、Track、WaveSurface 可复用规则，但需解除场景依赖。
- README 将 online play 列为非目标；实现时同步更新当前产品契约和模式数量断言。
- Playwright 已覆盖比赛流程、输入、存档、波浪、视觉和性能，可用于单机回归。

## 3. 技术方案

建议 Node.js + TypeScript 权威服务器，优先采用 Colyseus 的房间与状态同步能力。
已对照 Colyseus 与 Socket.IO 官方文档：前者提供游戏房间和状态同步；后者提供通信基础，
需要自行补齐更多游戏会话逻辑。实现前核对选定版本的 API、类型、Node 兼容性并锁定依赖。

服务器持有比赛真值：客户端提交油门、转向、加速及救援请求，服务器计算运动、碰撞、
奖励门、检查点、圈数和赛果。房主只拥有大厅管理权，关闭房主浏览器不停止服务器比赛。

- 新增 src/shared/：输入协议、可序列化状态、可在 Node 运行的模拟与规则。
- 新增 server/：服务入口、房间状态机、固定步长模拟、连接校验与资源回收。
- 新增 src/network/：连接、房间操作、输入发送、快照处理、预测校正。
- 渲染、镜头、音频、DOM 与输入设备留在客户端；可复用 Three.js 数学工具，不要求重写向量库。
- 单机和服务端使用同一份运动规则，避免维护两套物理实现。
- 初始参数：60 Hz 模拟、20 Hz 状态同步、输入按模拟序号批量发送；以性能实测调整。
- 本船本地预测并按服务器确认序号校正、重放未确认输入；远端船按快照插值。
- 波浪使用相同赛道参数与服务端模拟时间；快照包含影响运动的漂移、加速、计时等内部状态。
- 碰撞和门奖励以服务端为准；预测回放不重复触发音效或奖励，事件携带比赛 ID 和事件序号。
- 输入带比赛 ID、序号，服务端限制频率、队列和数值范围，拒绝旧局消息、非有限数及伪造状态。
- 本地调试钩子不具备修改线上服务器状态的能力。

## 4. 房间与异常规则（建议默认值）

- 状态：大厅 → 加载 → 倒计时 → 比赛 → 结算 → 大厅。
- 每次选赛道重置准备状态；所有客户端确认加载后统一倒计时，加载超时返回大厅并提示。
- 比赛开始后锁定席位，不接受新玩家中途参赛；原席位可在重连期限内恢复。
- 联机暂停只打开个人菜单并清空操作，不暂停比赛；R/Enter 不直接重置全场。
- 断线后清空操作，给予 15 秒重连窗口，使用不可猜测令牌恢复原席位并下发完整状态。
- 断线期间船正常减速并参与模拟；超时记 DNF 并退出碰撞，主动退赛立即记 DNF。
- 大厅房主离开后转移管理权；比赛中房主离开不影响其余人，重连不抢回管理权。
- 第一名完赛后启动 60 秒收尾倒计时；全部完赛/退赛或超时后统一结算。
- 设置整局最长时限（建议 10 分钟），避免无人完赛时房间永久运行。
- 成绩由服务端排序；同 tick 过线按线段穿越时间细分，相同时间采用稳定席位顺序。
- 救援由服务端按最后合法检查点定位，限制请求频率，不增加检查点进度。
- 再来一局回大厅重新准备；房间无人或闲置超时自动释放。
- 服务重启使内存房间失效，客户端显示提示并返回大厅；首版不做比赛持久化恢复。

## 5. 分阶段实现与验收

1. 建立基线并抽取模拟：安装锁定依赖，运行构建和关键单机测试；抽取后验证相同输入的
   固定步长回放，以及波浪、碰撞、漂移和检查点契约。交付仍可玩的单机版本。
2. 完成最小联机闭环：两客户端创建/加入房间、选赛道、准备、同步开局、移动、完赛、返回大厅。
   此阶段验收重点是服务端裁定结果，两客户端看到一致状态。
3. 补齐正式玩法：扩展到四人、船型/颜色与昵称区分、完整碰撞和奖励门、预测校正、远端插值、
   多人排名和赛后流程。两条赛道均可完成三圈。
4. 完成异常处理：掉线重连、房主管理权转移、失焦输入释放、加载失败、迟到消息、非法请求、
   房间回收、版本不匹配和服务器不可用提示。
5. 验证与交付：单元/服务集成测试、双浏览器端到端、四客户端联调、单机回归、部署说明，
   汇总证据后提交一个便于维护者审阅的功能 PR。

每阶段保持可运行；按阶段创建本地提交，避免把半成品作为最终交付。

## 6. 测试与验收标准

- 协议/规则：不能越权选图/开赛，不能超员，重复或旧输入不重复执行，不能跳检查点获取成绩。
- 服务集成：使用受控时钟覆盖开局、超时、重连期限、收尾倒计时和回收；避免依赖睡眠等待。
- 浏览器：至少两个独立 BrowserContext 完成建房至结算及重开，确认相同名单、赛道、名次和结果。
- 四客户端：两条赛道三圈完整联调，确认已完赛玩家不会停止其他玩家的比赛。
- 网络：受控注入 50/100/200 ms RTT、抖动和断线，验证无重复奖励、状态最终收敛、重连恢复。
- 性能：测量四玩家下帧时间、服务端 tick 耗时、流量和校正幅度；记录硬件及环境后制定门槛，
  不在实测前承诺特定服务器容量或弱网流畅度。
- 回归：npm run build、现有相关 Playwright 套件、视觉验证和生产预览性能检查。
- 视觉基线只因确认过的 UI 改动更新，不用批量更新掩盖回归。
